# 2026-08-22：Nav2 转向守卫与底盘可靠性复核

## 结论

本轮没有证明中长距离自主导航可用，但明确分离了三个问题：路径规划、位姿反馈和底盘通信/停机。当前候选地图、重定位和 Nav2 `ComputePathToPose` 仍可工作；最新受监督执行在转向阶段因 RGB-D 位姿与实物运动不一致而安全中止，未进入规划的前进阶段。这个 `FAIL` 是预期的保护结果，不能通过增大守卫阈值绕过。

底盘白板总线曾间歇性出现三个轮 ID 7/8/9 同时 `communication=-6`；插拔/重新供电后，只读高频诊断恢复通过，且三次抬轮零速度/断扭矩验证最终通过。恢复现象不足以确定根因，也不构成地面导航可靠性证明。继续真实导航前必须先完成带载短程的通信、反馈与停机门槛。

## 固定条件

- 地图数据库：`/data/slam/mapping/20260814T140025Z/rtabmap.db`。
- 建图/定位云台参考：黑板 serial `5B3D043224`，ID 7 raw `4066`、ID 8 raw `1924`；参考文件 `/data/config/gemini_gimbal_mapping_down_20deg_v1.json`。
- 云台在定位/导航期间必须保持该参考位；夹取或水平参考位不能混用。
- 底盘：白板 `/dev/ttyACM0`，只有 ID 7/8/9 可被导航程序寻址；白臂 ID 1--6 不参与。
- 本轮使用 `origin/codex/nav2-rotation-progress-guard`（`5e974c1`）的临时 Jetson worktree；主线 `main` 未被该试验分支替换。

## 已确认结果

### 1. 规划与执行不是同一个阶段

一次目标为 `(0.244, -0.108, 0°)` 的受监督导航，在重新定位后产生约 `0.254 m` 的路径；Nav2 路径计算约 `0.0013 s`。操作员等待的约一分钟来自 `--duration 60` 的相机/RTAB-Map/VO 启动和定位窗口，而不是 planner 的计算开销。`PLAN` 后的路径仍以当次实时 `map -> odom -> base_link` 位姿为起点，不使用上次的位置或按时间估算底盘位置。

该执行器当前是“Nav2 只做路径规划 + 项目自定义受监督跟随器”，尚未使用 Nav2 Controller Server。它在每个控制周期读取新到的 RGB-D odometry 并结合 `map -> odom` 校正；这属于实时闭环的雏形，但没有已验证的轮速/IMU 融合里程计。

### 2. 转向守卫正确阻止了错误前进

本轮约 6.8 s、35 个样本的执行记录中，所有命令 `linear_mps=0`，仅发出约 `-12 deg/s` 的转向命令。现场观察到底盘向右约转 `45°` 后略有位移；相同窗口中的 RGB-D 位姿只报告约 `15°` yaw 变化，并在应当近似原地转动时报告约 `0.051 m` 平移。程序以 `rotate-only RGB-D pose reported 0.051m translation; camera-only base feedback is inconsistent` 中止。

所以本次没有出现“规划前进 25 cm 但实际没有按路径走”的证据：程序在异常位姿反馈下没有放行前进。该阈值若被放宽，假平移会使执行器错误跳过路径航点，风险更高。

退出时本轮报告了多次零速度广播、三轮扭矩关闭和寄存器读回，未报告 shutdown error。它证明这一次停止过程被确认；不证明每次动态运行都能停止。

### 3. 白板/轮子通信可靠性仍是独立安全门槛

`tools/scan_servos.py /dev/ttyACM0` 多次能看到 ID 1--9，不足以证明运动中的连续通信可靠：它只做短时扫描。`tools/base_bus_cadence_diagnostic.py` 的一次只读 preflight 在 cycle 0 与 cycle 2 对 ID 7/8/9 的多个寄存器都得到 `communication=-6`，但中间 cycle 1 全部成功，表明存在间歇性共同链路失响应；软件日志不能区分 12 V 瞬降、白板/轮子 daisy-chain 线缆、接头、板端状态或其他共同原因。

重新插拔供电后，同一诊断通过：低频 `90/90`、高频 `900/900` 读取成功，最大读取延迟 `0.0021 s`。随后抬轮执行三次仅零速度/关闭扭矩诊断：前两次 `PASS stop_verified`；第三次先因 ID 8 `Present_Velocity=-50 raw` 的空闲抖动被 preflight 拒绝，重试后通过。为避免把小的静态反馈抖动误报为运动，独立分支 `codex/fix-base-stop-idle-jitter`（`20451e4`）把停止诊断的容差与已有停机读回的 `±60 raw` 一致；该补丁尚未并入 `main`。

这些结果意味着：目前可在现场监督下做短程诊断，不可据此恢复中长距离导航或忽略 `communication=-6`。

## 当前架构与缺口

当前相机路线为：Gemini RGB-D VO 提供连续局部运动，RTAB-Map 重定位提供 `map -> odom` 全局校正，执行器组合成 `map -> base_link`。它已能用于重定位和 planner-only，但原地转的视觉误差显示不能单独作为唯一底盘反馈。

已有但未完成实机验证的融合基础分支为 `origin/codex/fused-rgbd-slam`（`6bb856d`）。它的目标契约是：轮 ID 7/8/9 测得速度与 Gemini IMU yaw rate 经 `robot_localization` 生成连续 `odom -> base_link`，RTAB-Map 再发布 `map -> odom`。该分支的轮速物理单位、三轮符号、IMU yaw 轴/符号和协方差都标记为 unresolved，且 Jetson 当前 `forestbridge-xlerobot:slam-humble` 镜像尚未安装 `ros-humble-robot-localization`。因此不能直接切换或宣称已融合。

## 下一步门槛

1. **机械与通信**：断 12 V 后复核白板电源、白板→轮 7、轮 7→8、轮 8→9 的供电/数据线及运动时拉扯；随后在地面带载完成重复短前进、短横移和原地转向。每次必须有发送命令、三轮反馈、主动零速度、断扭矩读回和实际停止证据。任何 `-6` 或停机未确认即停止导航测试。
2. **只读传感器契约**：轮子抬起时记录 ID 7/8/9 的原始位置/速度，人工转轮确认符号、刷新率和物理比例；固定云台时读取 Gemini IMU，人工左/右转确认哪个 gyro 轴是底盘 yaw 及正负号。两项均不写扭矩、模式或速度目标。
3. **最小实时融合**：先以校验后的轮速提供平移、IMU gyro 提供短时 yaw，建立连续 `odom -> base_link`；保留 RTAB-Map 的 `map -> odom` 负责全局校正。先做只读/仿真图契约测试，再做抬轮与地面低速测试。
4. **导航恢复顺序**：先验证 ±20° 原地转不再产生虚假大平移，再验证 20--30 cm 直行的尺量、VO、轮速和融合里程计量级一致；同一短目标连续至少三次，全部安全停机后，才恢复 0.5 m 以上的地图目标。

## 不应采取的做法

- 不放宽 rotation-only 的 0.051 m 异常守卫来“让它继续走”。
- 不把静态 servo scan 通过当成运动时总线稳定。
- 不用 ACT/抓取的云台姿态进行该地图的定位或导航。
- 不直接用未验证的 fused 分支替换主线，也不在硬件可靠性门槛未通过时扩大导航距离。
